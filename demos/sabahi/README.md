# دمو پاسخ‌گویی تجاری صباحی

این پوشه یک نمونه پیشنهادی LUMA برای نمایش مسیر زیر است:

`RFQ → استخراج نیازمندی → تطبیق با محصول → کنترل ابهام → پیش‌نویس پاسخ → تأیید انسانی`

این یک prototype برای جلسه فروش است، نه سامانه تولیدی و نه محصول موجود صباحی.

## داده و مرزبندی

- اطلاعات محصولات از صفحات عمومی صباحی در `research.md` آمده است.
- سه مشتری، متن RFQ، مقدارها و سناریوها ساختگی هستند و در `data/sample-rfqs.json` ثبت شده‌اند.
- قیمت واقعی، موجودی، دیتاشیت خصوصی، گردش‌کار داخلی یا اطلاعات محرمانه صباحی در دمو وجود ندارد.
- در صورت نیاز به قیمت در جلسه، رابط عبارت «در انتظار قیمت‌گذاری» را نشان می‌دهد.
- امتیازهای تطبیق شاخص نمایشی برای اولویت بررسی‌اند، نه احتمال علمی یا تضمین فنی.

## اجرای محلی

از ریشه مخزن:

```bash
python3 -m http.server 4178 --bind 127.0.0.1 --directory demos/sabahi/app
```

سپس آدرس `http://127.0.0.1:4178/` را در مرورگر محلی باز کنید. برای تست خودکار مخزن، از اجرای headless استفاده می‌شود؛ این پروژه به بازکردن پنجره، پروفایل Chrome موجود یا سرویس بیرونی نیاز ندارد.

اجرای نمونه‌های مستقیم:

- `http://127.0.0.1:4178/?rfq=rfq-a-easy`
- `http://127.0.0.1:4178/?rfq=rfq-b-ambiguous`
- `http://127.0.0.1:4178/?rfq=rfq-c-multi`
- افزودن `&stage=1` تا `&stage=5` برای بازکردن مرحله‌ای که قبلاً تحلیل شده است.

## مسیر ارائه

روی «حالت ارائه» بزنید. مسیر شش‌مرحله‌ای با دکمه‌های «بعدی»، «قبلی» و «شروع دوباره» کنترل می‌شود. در گام آخر فقط تصمیم انسانی نمایش داده می‌شود؛ هیچ دکمه ارسال، اتصال قیمت یا تماس با مشتری وجود ندارد.

سناریوی A برای نشان‌دادن تطبیق واضح مناسب است. سناریوی B بخش مهم کنترل ابهام را نشان می‌دهد. سناریوی C نشان می‌دهد که چند قلم به‌صورت مستقل ساختاربندی می‌شوند و برای اقلام MPC با اطلاعات عمومی محدود، سیستم درخواست تأیید می‌کند.

## معماری

```text
index.html + styles.css
        │
        ├── data.js       داده public محصول + RFQهای synthetic
        ├── matcher.js    استخراج/تطبیق deterministic و قابل تعویض
        └── app.js        state، رندر مرحله‌ها، ارائه و کنترل انسانی
```

UI هر مرحله داده تحلیل‌شده را می‌خواند. `matcher.js` تابع `analyzeRFQ(rfqId)` را در اختیار UI می‌گذارد؛ در نسخه تولید می‌توان همین قرارداد را با API مجاز جایگزین کرد، بدون اینکه منطق نمایش و approval به مدل یا سرویس خاصی گره بخورد.

## اگر به تولید برسد

قبل از هر اتصال واقعی باید مسیر RFQ با صاحب فرایند صباحی اعتبارسنجی شود، مرجع رسمی SKU و دیتاشیت تعیین شود، مالک قیمت/موجودی مشخص شود، سطوح دسترسی تعریف شوند، و نمونه‌های واقعی پاک‌سازی‌شده برای اندازه‌گیری baseline فراهم شوند. انتخاب محصول، قیمت و انتشار پاسخ باید در تمام مراحل نقطه تأیید انسانی داشته باشد.

## محدودیت‌ها

- منطق فعلی برای سه fixture مشخص نوشته شده و ادعای استخراج عمومی از هر متن دلخواه ندارد.
- اطلاعات MPC در صفحه عمومی در سطح دسته محصول است؛ گرید، خلوص، موجودی و قیمت عمداً UNKNOWN باقی می‌مانند.
- زمان‌ها و درصد تکمیل فقط وضعیت همین نمونه ساختگی را نشان می‌دهند و صرفه‌جویی عملیاتی صباحی نیستند.
- دمو deploy عمومی نشده و برای استفاده بیرونی باید ابتدا بازبینی حقوقی، برندسازی و محتوایی شود.
